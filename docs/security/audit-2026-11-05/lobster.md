## Findings (all open; report-only — no fix attempted)

### F-LOB-01 — Hand-editable text parser recurses on input nesting with no depth cap
- Where: `internal/codegen/lobstertable/runtime/text_form.lobster:109` (`t_parse_value`), the recursive call at `text_form.lobster:127`, entered from `text_load` at `text_form.lobster:779`.
- What untrusted input can reach/do: a text-form document handed to `schema_rt.text_load` (or re-parsed by `text_edit`, `text_form.lobster:793`) whose value nesting is a long run of `(` bytes. Each `(` consumes one input byte and one recursive `t_parse_value` frame, and `TextParser` carries no depth field, so nesting depth — and therefore call-stack depth — is bounded only by input length. Every other text reader in this leg carries an explicit cap (JSON depth 128 at `json.lobster:24`, message skip depth 128, retain depth 64). A deeply nested document exhausts the Lobster VM's stack instead of earning a parse refusal. The schema-driven fill that follows (`t_value_into`, `text_form.lobster:680`) walks the already-parsed tree, so the parser is the unbounded stage.
- Severity: **medium** (stack exhaustion from a small, linearly-sized input on a text reader; no memory unsafety beyond the host process's stack failure).
- Suggested reduction: carry a depth count in `TextParser`, refuse above a fixed cap (128, matching the JSON reader) in `t_parse_value` before recursing, and name the refusal with the existing `text_*` failure names.
- Pin that would fix it: a lobstertable runtime test feeding `text_load` a document nested past the cap and asserting a nil document with the named failure, plus a document nested just under the cap still loading. Named only — not created under report-only.
- PATHS-PROPOSED: `internal/codegen/lobstertable/runtime/text_form.lobster` is inside PATHS; the fix is surgical there, but no fix was attempted on this report-only card.

### F-LOB-02 — Hand-editable text numbers expand a decimal exponent into a digit string sized by the exponent
- Where: `internal/codegen/lobstertable/runtime/text_form.lobster:352` (`t_dec` accumulates the exponent with no cap), the expansion loops at `text_form.lobster:390`–`text_form.lobster:391` (`t_int_token`) and `text_form.lobster:423`–`text_form.lobster:424` (`t_fixed_token`).
- What untrusted input can reach/do: a short numeric token in a text-form document with a large positive exponent (on the order of `1e100000000`, twelve input bytes). `t_int_token` and `t_fixed_token` materialize the value by appending one `0` character per exponent step before converting digit by digit, so allocated memory and conversion time are sized by the exponent's *value*, not by the token's length, and repeated one-character concatenation makes the cost worse than linear in the result. The JSON reader in the same leg stops accumulating an exponent at 100000 (`json.lobster:604`) and never expands digits this way; the text reader has no equivalent guard, and a many-digit exponent also wraps the uncapped `exp * 10` accumulation at `text_form.lobster:352`.
- Severity: **medium** (memory and time exhaustion from a constant-size token on a text reader).
- Suggested reduction: refuse a token whose expanded digit count passes what a 128-bit value can hold (39 digits) before expanding, in both `t_int_token` and `t_fixed_token`, and cap the exponent accumulation in `t_dec` the way `j_token_decimal` caps it.
- Pin that would fix it: a lobstertable runtime test asserting `text_load` refuses a document carrying an integer token with an exponent past the digit cap, and still loads the largest in-range exponent spelling. Named only.
- PATHS-PROPOSED: `internal/codegen/lobstertable/runtime/text_form.lobster` (inside PATHS; not attempted, report-only).

### F-LOB-03 — JSON string scan stores an unpaired surrogate escape as U+FFFD instead of refusing it
- Where: `internal/codegen/lobstertable/runtime/json.lobster:1039`–`json.lobster:1040` (`j_scan_unit`), reached by every JSON string field through `j_scan_text` and by wide strings through `j_scan_wstring` (`json.lobster:1133`).
- What untrusted input can reach/do: a JSON text for a `string(N)` or `wstring(N)` field carrying a lone `\uD800`–`\uDFFF` escape that is not one half of a pair. The wire readers in this leg refuse exactly that shape (packet `wstring` at `internal/codegen/lobster/read.go:435`–`read.go:438`; table wide text at `load.lobster:390`–`load.lobster:406`), but the JSON reader rewrites the code point to the replacement character and accepts the text, so two different JSON texts decode to one stored value and the JSON form disagrees with the wire forms on the same field. This matches the Go engine's current behavior, so it is a shared-engine divergence as well as a leg one; it is recorded here because the leg's emitted reader is the surface that stores it.
- Severity: **low** (acceptance divergence on a text form; the stored value is well-formed and bounded, and no bound is exceeded).
- Suggested reduction: refuse a lone surrogate escape in `j_scan_unit` with the reader's malformed verdict, as the wire paths refuse it; keep the paired-escape join at `json.lobster:1031`–`json.lobster:1037` unchanged.
- Pin that would fix it: a lobstertable JSON test asserting a lone-surrogate escape in a string and a wide-string field is refused while a paired escape still loads. Named only.
- PATHS-PROPOSED: `internal/codegen/lobstertable/runtime/json.lobster` (inside PATHS; not attempted, report-only). The Go engine's matching behavior is outside PATHS.

### F-LOB-04 — JSON duplicate keys are counted and accepted, last value winning
- Where: `internal/codegen/lobstertable/runtime/json.lobster:1407`–`json.lobster:1408` (table keys), `json.lobster:1705` (enum-keyed arrays), `json.lobster:2275` (maps); `json_read` at `json.lobster:2364` returns the record whenever the parse itself succeeds.
- What untrusted input can reach/do: a JSON object that names the same field, keyed slot, or map key twice. Each site increments `report.duplicate` and keeps the later value, and no JSON entry point treats the counter as a refusal — there is no strict JSON variant analogous to `load`/`load_strict` for the wire form — so a duplicated key is accepted data on this form while SPEC-TABLES §16's duplicate rule names it a refusal. The hand-editable text form in the same leg does refuse duplicates (`text_form.lobster:490`, `text_form.lobster:523`). This also matches the Go engine's current tolerant behavior.
- Severity: **low** (fail-open on a duplicate the spec refuses; memory-safe, and the report does count it).
- Suggested reduction: make `json_read` refuse (nil, with the duplicate named) when `report.duplicate` increased during the read, leaving the counter semantics of the tolerant internals unchanged.
- Pin that would fix it: a lobstertable JSON test asserting a duplicated field key and a duplicated map key each refuse under `json_read`. Named only.
- PATHS-PROPOSED: `internal/codegen/lobstertable/runtime/json.lobster` (inside PATHS; not attempted, report-only).

### F-LOB-05 — Fixed-form tolerant load leaves earlier caller records scattered when a later record fails
- Where: the generated load loop emitted at `internal/codegen/lobstertable/fixedevolve.go:1526`–`fixedevolve.go:1533` (`<Name>FixedScatter` writes `values[k]` per record), the early refusal returns at `fixedevolve.go:1524`–`fixedevolve.go:1525` and `fixedevolve.go:1530`–`fixedevolve.go:1531`, and the strict wrapper at `fixedevolve.go:1427`–`fixedevolve.go:1439`.
- What untrusted input can reach/do: a form-3 file whose later record fails its text refusal or `fixed_run` after earlier records have already been scattered into the caller-supplied `values` array. The call answers -1, but the strict wrapper only resets caller records on the path where the tolerant load returned a count and the report then names an error; on the -1 paths the already-scattered prefix stays in caller storage, beside whatever the array held before the call. The non-finite-float path in the same loop does reset every record the call wrote, so the reset discipline exists and is applied on one refusal path only.
- Severity: **low** (a caller that reads `values` after a -1 answer sees a half-updated batch; the load itself stays inside its buffers).
- Suggested reduction: reset `values[0..k]` on every refusal return inside the scatter loop, as the non-finite path already does, or scatter into scratch records and publish only on success.
- Pin that would fix it: a lobstertable fixed-form test loading a two-record file whose second record is damaged and asserting both caller records still hold their pre-call values after a -1 answer. Named only.
- PATHS-PROPOSED: `internal/codegen/lobstertable/fixedevolve.go` (inside PATHS; not attempted, report-only).

### F-LOB-06 — Packet readers fill caller storage progressively, so a refused read leaves a half-filled value
- Where: `internal/codegen/lobster/read.go:196` (`emitReadStruct`), the union tag store at `read.go:231` before its arm is read, and the counted-array count store at `read.go:327` before its elements are read; `schema_wire.lobster:16` likewise validates a string payload only after `serialize_bytes` has copied it (`read.go:391`–`read.go:396`).
- What untrusted input can reach/do: any packet buffer that a generated `Read*` refuses part-way. The read writes each field into the caller's pre-allocated value as it goes and answers false at the first refusal, so fields before the failure hold wire values, the field at the failure may hold a copied-but-unvalidated payload, and later fields hold what the value held before the call. The stream is latched and the contract is that a false answer discards the value (stated at `read.go:7`–`read.go:17`), but nothing in the generated code enforces the discard; a caller that ignores the boolean reads a mixed old/new record. This is the storage principle every leg shares (SPEC §6.1), recorded here as the leg's instance of it.
- Severity: **low** (caller-visible partial state on a refused read; safe for every caller that honors the documented false answer).
- Suggested reduction: none in the generated reader without abandoning the fill-in-place contract; keep the discard rule and state it on each generated `Read*` doc comment (the comment at `read.go:199`–`read.go:201` already says a refusal latches and answers false). If a staging reader is ever wanted, it is a new surface, not a fix here.

## Generator audit notes (no finding)

- **Identifier and literal safety.** Schema identifiers reach generated code only as checked names: the packet generator refuses a Lobster keyword or the runtime namespace as a package or declaration name (`internal/codegen/lobster/lobster.go:139`–`lobster.go:164`), the table generator refuses a package that collides with any namespace-scope runtime binding (`internal/codegen/lobstertable/runtime_package_names.go:71`), a schema file whose module would collide with an emitted runtime module is refused case-insensitively (`lobster.go:170`–`lobster.go:179`), and the unit-registry filename collision is refused before output (`internal/codegen/lobstertable/lobstertable.go:186`–`lobstertable.go:204`). The runtime's own names are claimed in `internal/tablenames/lobster.go:28` and held to the emitted runtime by the compiler's name tests. Every schema-derived string (names, docs, tags, defaults, layouts) is emitted through `lobster.StringLit` (`lobster.go:828`–`lobster.go:841`), which escapes every byte outside a small safe set as `\xNN`, so no quote, backslash, brace (Lobster string interpolation), or newline from schema text can terminate or interpolate a generated literal. Doc comments are emitted only as `//` line comments split per source line (`lobster.go:372`, via `ir.DocComment`), so a doc newline cannot inject a code line. Output filenames are the schema file's `Base` plus a fixed suffix (`lobster.go:115`, `lobstertable.go:120`); the generators build no shell command, path, or import from field or variant names — imports are unit module basenames recorded by the generators themselves (`lobster.go:291`–`lobster.go:306`).
- **Reserved runtime module names are emitted only when used.** A table-free unit emits only its descriptor dependencies (`internal/codegen/lobstertable/lobstertable.go:182`–`lobstertable.go:199`), so an unused codec's runtime filename cannot refuse a packet-only schema.
- **Write side.** Packet and table writers validate by the write contract (SPEC §5, `docs/SECURITY.md`: write-side validation is the caller's); every read-side bound cited above is enforced unconditionally, including under `--runtime-no-asserts`, because the readers use ordinary conditionals rather than `assert` (the one assert-guarded surface is the trusted decoder in F-LOB-07). Enum-keyed `Slot` (E23) refuses by VM bounds error, which that flag keeps.
- **Allocation shape.** Every wire-driven allocation in E10–E13 and E16–E18 is proportional to framed input bytes: lengths pass `has` before a copy or substring, list and map counts pass the int32 storage cap before elements are materialized, each materialized element first consumes framed bytes or fails, and the id trailer is capped at 4096 entries. The trailer's duplicate scan is quadratic in that capped count (`load.lobster:1842`–`load.lobster:1850`, at most 4096 entries) — bounded, deliberately, and not a finding. The two text-form exceptions are F-LOB-01 and F-LOB-02.
- **Partial state, table forms.** The tolerant wire load discards its record on malformed, missing-required, and non-finite outcomes (`load.lobster:2042`–`load.lobster:2053`); `json_read_into` is the documented exception — its own comment states the caller's record keeps what was placed before a stop (`json.lobster:2347`), and `json_read` withholds the record on failure (`json.lobster:2364`–`json.lobster:2368`). The batch message read discards every body on damage (E17). The fixed-form caller-storage exception is F-LOB-05.
