# Rust tables read: a line-level profile of the flat decode body (#358)

2026-10-16. **The ratios are certified on amd-2** (`b2`, AMD Ryzen 7 255, 8 cores / 16
threads, Linux 7.0.0-38), in windows that the BENCH-STANDARD §2.6 control legs certify
`window: OK`. Schema is `sprint/schema-rust` at `5c8e5ba3b` with this card's commits.
The toolchain is rustc/cargo 1.98.1, g++ 15.2.0 and clang++ 21.1.8, with serialize v1.16.2
(`93b8ea2a`, the `SERIALIZE_PIN`) and serialize.rs `5be639fd`. Raw rows, control legs, the
load log of every boundary, the window verdicts and the driver are in
[`bench/results/2026-10-16-rust-tables-read-amd-2/`](../../bench/results/2026-10-16-rust-tables-read-amd-2/).
The line-level profile below was taken first on hetzner2 (Ryzen 9 7950X3D, g++ 13.3.0,
clang++ 18.1.3) in a window that was not quiet. Its PMU counters were taken again on amd-2
between two controls, and they have the same shape. The hetzner2 sittings are kept in
[`bench/results/2026-10-16-rust-tables-read-hetzner2/`](../../bench/results/2026-10-16-rust-tables-read-hetzner2/)
as a diagnostic. They carry no window verdict, and no ratio here comes from them.

## The answer first

**The gap #358 names is gone. On the surface Rust has today, Rust reads faster than C++:
1.36x the clang build and 1.76x the g++ build** in the certified base sitting, and 1.39x and
1.77x in the certified confirmation sitting (per-round medians; ranges below). The
uncertified hetzner2 sittings said the same, at 1.43x and 1.70x. The 0.72x in the issue comes from
[`bench/tables/results/2026-09-03-rust-inline-arm64-macbook.md`](../../bench/tables/results/2026-09-03-rust-inline-arm64-macbook.md):
a pairing check on an M2 Air that measured the TOLERANT wire (form 1) of the old
`BenchTable.schema` corpus. That measurement cannot be taken again. The Rust backend
no longer emits a form-1 codec for a fixed table: `schema generate --lang rust bench/corpus/BenchTable.schema` emits `table_mixed_fixed_load`/`_save` and nothing else, and
`bench/tables/README.md` already says the Rust runner is the FIXED form's (form 3) leg for
`bench/paired`. So the "flat decode body" today is `fixed_table_fixed_load`, and this note
profiles that.

**No emitter change was made.** A change to close a gap needs a gap, and the profile shows the
difference runs the other way. The largest identified cause of the difference is on the C++
side: **C++'s read-side clamp pass is a scalar loop with a memory round trip for every
element, because its `int32_t & clamped` counter may alias the value being clamped.** Rust's
`&mut i32` cannot alias, so the same loop is vectorized. In the hetzner2 profile that pass
alone differs by 77 ns per record, more than the whole 67 ns between Rust and clang. Landing the record costs about the
same on both sides (Rust's copy plus scatter is 72 ns, clang's plan 69 ns), and Rust pays about
10 ns that C++ does not, in the scatter and the per-call framing.

## The measurement

Paired, interleaved, one sitting. Each round runs every binary once (`--round K`, one warmup
and one measured run, `--iterations 4000000`, which is 62,500 whole rotations of the 64
records), and the order rotates one place each round. Read is DERIVED (1/round_trip −
1/write), as the runner itself derives it. The ratio is taken per round, and its median is
reported. The binaries are the ones `bench/paired`'s build step makes (`go run ./bench/paired -mode build -langs cpp,rust`): the paired unit (`Bench.schema` + `FixedTable.schema`)
regenerated by this revision's `cmd/schema`, the C++ runner at `-O3 -DNDEBUG -ffp-contract=off -fno-rtti`, and the Rust runner from `cargo build --release` at
`CARGO_PROFILE_RELEASE_OPT_LEVEL=3`. `bench/paired` builds with `c++`, which is g++ on this
host, so g++ is the driver's C++ build. clang is the build that shares rustc's backend. Both
are shown. Every binary passed `--gate` (table corpus `066b2822b3e5d487`, control corpus
`fd0748942dc6ae09`) before any clock. Their sha256 are in `host.txt`, and they are
byte-identical to the same build made on amd-3.

**The window is certified, by the read arm's rule.** The sitting driver
(`tools/sitting.sh`) follows the C++ read arm (`bench/paired`, 2ac615b86) and BENCH-STANDARD
§2.5–§2.6:

- **Control legs.** Each sitting begins and ends with the same leg, the C++ family `gen`
  runner (`packet-cpp`, g++ 15.2.0, `-O3 -DSERIALIZE_RELEASE`, round 0, pinned). Every control
  row (`bench_mixed` write and round_trip) has to agree with itself start-to-end within 5%.
- **Foreign processes.** A known build or bench process above 5% CPU in the 1 s `top` sample
  taken at any round boundary refuses the sitting. Every other process above 5% is listed in
  `*.load.txt`. None appeared in the certified sittings.
- **Pinning.** Every leg and every control runs under `taskset -c 7`. This host has no
  `isolcpus`, so core 7 is declared rather than kernel-isolated. Its SMT sibling (cpu 15) and
  all the other cpus are measured from `/proc/stat` over the window.
- **Load.** The pre-check is load1 < 1.0 with no build or bench process present. The load
  recorded during a sitting includes that sitting's own pinned leg, which is about 1.0.

## The named cause: the C++ clamp loop cannot keep its counter in a register

This is clang's inner loop for the 80 `MixedStat` clamps (`BenchMixedFixedClampBody`):

    8200: cmpl   $0x100,0x244(%rbx,%rax,8)
    820b: sbbl   $0xffffffff,(%r14)        ; clamped += (stat_id > 255), in memory
    820f: mov    0x244(%rbx,%rax,8),%edi   ; reload stat_id   (35% of the function's samples)
          ... cmovae, store ...
    8226: mov    0x248(%rbx,%rax,8),%edi
          ... cmp ...
    8235: adcl   $0x0,(%r14)               ; clamped += (delta out of range), in memory
    8239: mov    0x248(%rbx,%rax,8),%edi   ; reload delta     (43%)
          ... cmov, cmov, store ...
    825c: movslq 0x4c4(%rbx),%rdi          ; reload stats_count, every iteration
    8266: jl     8200

`clamped` is an `int32_t &` and every field of `MixedStat` is a 32-bit integer, so the compiler
must assume a store through `clamped` can change `value.stats[i]`, and that a store to
`value.stats[i]` can change `clamped` or `value.stats_count`. Each element therefore does a
read-modify-write of the counter in memory, reloads the field it just compared, and reloads the
loop bound. Rust's `mixed_stat_fixed_clamp_body` takes `&mut MixedStatRow` and `&mut i32`,
which the language guarantees disjoint, so LLVM keeps the counter in a register and vectorizes
the loop (`paddd`, `pcmpgtd`, `pand`/`pandn`/`por`, `packssdw` in the hot block). This is the
same mechanism the 2026-09-03 record found on the WRITE side of the old wire (an out-of-line
`uint8_t *` cursor aliasing in C++, a `&mut [u8]` not aliasing in Rust), now on the read side
and pointing the other way.

**Checked by experiment, not only read off the assembly.** The two counters were marked
`__restrict` in a scratch copy of the regenerated C++ header (`int32_t & __restrict clamped, int32_t & __restrict damaged`, seven declarations, nothing else; `tools/setup.sh` makes it).
Both compilers built it, every build passed `--gate`, and it was timed in its own
interleaved, certified sitting on amd-2 (`exp-restrict.*`, 7 rounds, 03:14:35–03:16:45 UTC,
**window OK**, control delta 0.19%, load1 0.86–1.05, no foreign build or bench). The first
take of this sitting was refused (two `go` processes) and is kept in `refused/attempt-03-exp`.

| build | read ns/rec (median) | vs its own base build, per-round median [min, max] |
|---|---:|---:|
| clang, base | 198.2 | — |
| clang, `__restrict` counters | 161.1 | **1.215x faster [1.166, 1.269]** |
| g++, base | 252.8 | — |
| g++, `__restrict` counters | 249.2 | 1.019x [0.996, 1.061] (no gain) |
| Rust, base | 143.9 | 1.380x clang base [1.322, 1.410]; 1.116x clang-restrict [1.088, 1.180] |

On clang, one keyword closes 37 of the 54 ns between Rust and clang's read. g++ does not gain
from it, here or on hetzner2, where g++ 13 was 0.928x, a little slower. So g++'s clamp loop is
held by something else. That was not chased: it is on the C++ side, and it is not this card's
surface. The hetzner2 take, uncertified, gave clang 1.251x and Rust/clang-restrict 1.163x.

## What this card does not change, and why

- **No Rust emitter change.** The card allows one change, in `internal/codegen/rusttable/rusttable.go`
  or `variablecodec.go`, if the profile supports one that closes the gap. There is no gap to close.
  The Rust form-3 reader is also emitted by `internal/codegen/rusttable/fixedform.go` and
  `fixedruntime.go`, which are outside this card's PATHS, and its output under
  `generated/bench/paired/rust/` is too. A measured negative is the result.
- **The Rust-side costs C++ does not pay are named, and left as a follow-on.** The scatter
  (37.9 ns, about 26% of Rust's read) is a second pass over the record that C++ does not need,
  because C++ lands the plan straight into its native struct. Fusing scatter and clamp, or
  landing the identity plan straight into the `#[repr(C)]` row, is the obvious next Rust lever.
  It belongs in `fixedform.go`, it needs its own card, and it would widen a lead rather than
  close a gap. `table_fixed_holes` builds a `[u8; BODY]` cover map and scans it on every call
  even for the identity plan, whose hole list is empty by construction. That is 1.5%: small,
  but a constant the emitter could fold.
- **The C++ fix is named, not made.** Changing the clamp counters to locals (or `__restrict`)
  belongs in the C++ table emitter. It is out of this card's PATHS and stream. The experiment
  above measures it for clang.
- **Both builds target baseline x86-64 (SSE2).** Rust's vectorized clamp emulates `min`/`max`
  with compare-and-blend, because `pminsd` is SSE4.1. A `target-cpu` build would move both
  sides, and it is not how either leg is built. Not measured.
- **The committed paired units are stale at this base.** `generated/bench/paired/cpp` does not
  compile as committed (`FixedTableFixedGuards` was not declared in this scope). Both it and
  `generated/bench/paired/rust` differ from what this revision's `cmd/schema` emits. The
  paired driver regenerates both before building, so the bench is unaffected. That is why
  hetzner2's sittings showed six dirty paths, and amd-2's `host.txt` shows two
  (`generated/bench/paired/cpp/{BenchTable,FixedTableTable}.h`): the regenerated files and
  nothing else.
  The committed copies are the driver's to refresh, not this card's.

## Reproducing it

The certified sittings are reproduced on a Linux bench (never the Studio) by the scripts
committed beside the rows, in `bench/results/2026-10-16-rust-tables-read-amd-2/tools/`:

    bash tools/setup.sh      # clone schema + serialize v1.16.2 + serialize.rs, paired build, clang and __restrict legs, --gate each
    bash tools/hunt.sh OUTROOT 8 DEADLINE_EPOCH   # wait for load1 < 1 and no build/bench, then base + confirm (+ exp)
    bash tools/sitting.sh NAME OUT ROUNDS CORE BIN...   # one sitting: control, rounds, control, load, verdict
    python3 -I tools/summarize.py OUT/base.csv table-rust table-cpp-clang table-cpp-gcc
    bash tools/pmu.sh OUT    # perf stat counters between two controls

`summary.txt` is `summarize.py`'s output for the three certified sittings. The commands the
paired build runs, for building by hand, follow. The hetzner2 sittings were built this way:

From a checkout beside `serialize/` and `serialize.rs/`, on the Linux bench (never the Studio):

    go build -o build/paired/schema ./cmd/schema
    for l in cpp rust; do build/paired/schema generate --lang $l --out generated/bench/paired/$l \
        bench/corpus/Bench.schema bench/corpus/FixedTable.schema; done
    F='-std=c++17 -Wall -Wextra -Werror -ffp-contract=off -fno-rtti -O3 -DNDEBUG -DBENCH_OPT="O3"'
    g++     $F -Wno-class-memaccess -Wno-type-limits -DBENCH_MATCHED -Igenerated/bench/paired/cpp \
        -I../serialize bench/tables/cpp/table_main.cpp -o build/paired/table-cpp-gcc
    clang++ $F -DBENCH_MATCHED -Igenerated/bench/paired/cpp -I../serialize \
        bench/tables/cpp/table_main.cpp -o build/paired/table-cpp-clang
    ln -sfn "$PWD/../serialize.rs" build/paired/serialize.rs
    BENCH_OPT=O3 CARGO_PROFILE_RELEASE_OPT_LEVEL=3 cargo build --release \
        --manifest-path bench/tables/rust/Cargo.toml --target-dir build/paired/rust
    # then per round K, rotating the order, each pinned:
    taskset -c 15 <binary> --indexed --wire-dir bench/paired/corpus \
        --variant-dir bench/paired/corpus --round K --csv --iterations 4000000

For the profile, rebuild with `CARGO_PROFILE_RELEASE_DEBUG=2` (Rust) and `-g` (C++), then
`perf record -e cycles` and `perf report --sort srcline`. On a box with
`perf_event_paranoid` at 4, `sudo perf` reads the counters and changes no setting.
