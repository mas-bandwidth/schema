# R32 notes — retire for real: a retired version is refused by name, once, idempotently

## Law citation
docs/FIXED-FORM-ALGORITHM.md:552-553:
"The floor is one number and the lineage is one array, so 'retired' is an index cut and the operator's two
answers stay distinct: below the floor is layout_unsupported (upgrade the client), outside the lineage is
layout_newer (ship the reader). A retired entry stays in the lineage forever."

Also: docs/FIXED-FORM-ALGORITHM.md:441
"per entry: a RETIRED mark and its reason (`schema lock --retire T@<hash>`) | the floor, and layout_unsupported"

docs/SPEC-TABLES.md:854 mentions "each refused by name (§11)" for retirement-related refusals.

## Call site in production
compiler/target_cpp.go:38 calls cpptable.GenerateLineage(u, lineage.Lock()) which emits lineage data.
internal/codegen/cpptable/lineage.go:350 implements lineageFloor() which computes the floor from
lockfile.Floor(g.lock, want) — that function (internal/lockfile/lineage.go:375-383) returns one past
the highest Retired index. The emission happens in fixedform.go:605-660 emitFixedLineage(). The
runtime check is in fixedform.go:532-534 where LOAD checks `if ( lineage_at < floor_at )`.

## Production path exercised
My test saves a vold_floor record using vold_floor::FlooredFixedSave (fixedform.go writer), then loads
via vnew_floor::FlooredFixedLoad (fixedform.go reader). The reader iterates FlooredFixedLineage[] to find
the hash, checks if the index is below FlooredFixedFloor (set to 1 by fixtureFloor map), and returns
report->reason = layout_unsupported when lineage_at=0 < floor_at=1.
