### A prediction refuted, plainly

From the const-params experiment's numbers (raw macro path: reads 5-8x
faster than writes) the expectation was read >> write across the board.
FALSE for generated code: `test` (762 w vs 532 r), `probe_header` (1040 w
vs 552 r), `inputpacket` (39 w vs 35 r), `testdata` (17 w vs 14 r) and
especially `message_batch` (74 w vs 30 r) all write FASTER than they read.
The read path pays for range validation, branch zeroing, and — in the batch
— `Message`'s constructor memset plus per-arm `= T{}` re-initialization
(see hotspots). Reads only win big where wide raw bit reads dominate
(probebits 495 r vs 83 w; rigidbody 82 r vs 24 w).

## Predictions for the ryzen run — STATED BEFORE MEASURING

Recorded before any bench ran on `space` (see git history: this file lands
before the ryzen tables do). Host facts known in advance: Ryzen x86_64,
16 cores, isolcpus=1-15, the game server RUNNING with one pinned thread per
isolated core, ssh jailed to core 0 → bench on shared core 0, labeled
NOISY. g++ 13.3 and clang 18.1 both available; g++ is the primary
(production Linux toolchain).

1. Spreads much worse than the M2's (core 0 also serves irqs, ssh, and a
   dozen game-server aux threads): median spread 5-20%, occasional wild
   outliers. Medians still usable.
2. Per-benchmark Release rates 0.4-0.8x of the M2 for most benchmarks; the
   same overall shape (test and probe_header fastest by msgs/s, testdata
   slowest, batch read << batch write).
3. The write<read refutation above holds on x86_64 too — it is structural
   (validation + zeroing on read), not an arm64 artifact.
4. g++ and clang++ within ±25% of each other per benchmark, no uniform
   winner.

Verdicts, measured after: **1 HELD** (spreads 1-26%, medians usable).
**2 PARTIALLY REFUTED** — writes land 0.4-1.0x of M2 (probebits write even
ties it), but READS fall to 0.25-0.35x on several benchmarks (rigidbody 24
vs 82, probebits 124 vs 495 under g++): the M2's read advantage is the
wide load/store engine, and core-0 sharing cannot explain a 3x gap.
**3 PARTIALLY REFUTED** — message_batch and inputpacket write>read
everywhere, but g++ flips test/probe_header/testdata back to read>write;
the balance is compiler-dependent, only the batch result is structural.
**4 STRONGLY REFUTED** — clang 18 beats g++ 13 by up to **4x** on
tiny-message writes (test 505 vs 139 M msg/s, probe_header 496 vs 124),
not ±25%. See hotspot 2: g++ leaves the per-field stream calls outlined.

## Hotspots (evidence-backed; seeds for the optimize pass — nothing optimized yet)

**1. `Message` union zeroing dominates real message-stream decode — both
platforms.** The union member is Block-sized (2008 B), so every
`ReadMessage` zero-fills ~2 KB to decode a ~25 B message: `Message m;`
ctor memsets the whole struct, then the matched arm does `message.chat =
Chat{};` again. Evidence: EPYC `perf annotate bench_batch` = 46.96% +
8.06% + 5.61% of self-cycles on three `rep stos` sites (60.6% total,
memset) + 1.05% `rep movsq`; M2 `sample` top-of-stack has
`_platform_memset` second overall (334 samples; callers: the batch read
loop in `main` at 321, inside `ReadMessage` 88+46). It is why
message_batch read is 2.4-3.2x slower than write on every
platform/compiler while nothing else in the batch shows up. Obvious
afternoon candidates: zero only the matched arm's bytes, or zero only up
to the arm's size instead of the union's.

**2. g++ outlines the per-field stream calls; clang inlines them — worth
up to 4x on small messages.** Under g++ 13 `-O3`, `perf` shows
`serialize::BitWriter::WriteBits` (4.53% self), `FlushBits` (2.12%) and
`serialize_double_internal<ReadStream>` (4.62%) as standalone hot symbols
called per field — `perf annotate` on WriteBits shows ~30% of its time in
call boilerplate (`endbr64`/reg-shuffle/`ret`). clang inlines these into
the generated Write*/Read* bodies. Same-machine result: test write 505
(clang) vs 139 (g++), probe_header 496 vs 124, probebits read 267 vs 124.
This is the same mechanism the const-params experiment isolated ("the
wins live at inliner budget spills"); its compile-time-parameter surface,
or forced inlining of the hot stream ops, is the lever — measure with
this harness either way.

**3. testdata (and byte/string paths generally) are bytes-loop bound.**
The one benchmark where the M2 reads SLOWER than it writes (13.7 r vs
16.8 w). M2 `sample` in the testdata window: `ReadTestData` top (363),
`WriteTestData` 243, `BitWriter::WriteBytes` outlined even under clang
(144), plus `SerializeInteger64`, `serialize_compressed_float_internal`,
`SerializeAlign` and `ReadStream::SerializeBytes`. The 17-entry
`fixed_bytes` array rides `write_bits(...,8)` per byte, and the string
path re-walks the text on read (byte copy, then the interior-null scan).
Candidates: byte-array fast path over the aligned-bytes route, fold the
null scan into the copy.

Non-candidate worth recording: rigidbody read on M2 (82 M msg/s over 13
doubles) is already near the raw-bitpacker read ceiling — double fields
are bit-copies, nothing to shave there.
